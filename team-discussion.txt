AGENDA ITEM 5: SEAT LOCKING STRATEGY
--------------------------------------------------------------------------------
[ ] This is a core architectural decision for the booking engine.

The Problem:
  Two users select the same seat at the same time.
  We need to guarantee only ONE of them gets to pay.

Options:
  A) DB-based hold   → SeatHold table with held_until timestamp + scheduled cleanup job
  B) Redis-based TTL → Faster, auto-expiring, but adds Redis to infrastructure

DECISION LOCKED: Option B (Redis-based TTL)
  [x] Redis Key: `seat_hold:{sessionId}:{seatId}` → value: `{userId}`
  [x] Hold duration: 10 minutes (600 seconds)
  [x] Atomic acquisition: `SET ... NX EX 600` (guarantees atomic locking; fails if held)
  [x] Auto-cleanup & real-time release: Redis keyspace notifications (`notify-keyspace-events=Ex`)
      trigger Spring Boot listener to immediately broadcast `AVAILABLE` to all WebSocket clients.
  [x] Local setup: Handled via Docker Compose (PostgreSQL 15 + Redis 7), so zero manual install.
